# 插件规模无关的加载器：让「以后新增任何插件」都不再拖慢客户端

`docs/17` 解决的是**当时那一次插件组合**的组合问题（重复 reload、样式与观察器泄漏）。
这一篇换主体：**以 BetterNCM 自身（加载器 `loader/framework.js` + 后端 `tools/ncm_host.mjs`）为优化对象**，
目标是让成本不随插件数量增长，并且让**任何一个插件都无权拖垮其它插件**。

一句话：不是把已知插件调快，而是让未知插件不可能把加载器变成瓶颈。

---

## 1. 优化前的三条真实缺陷（都有实测）

| # | 缺陷 | 实测后果 |
|---|---|---|
| 1 | 插件加载是**严格串行链**：`chain = chain.then(() => loadPlugin(p))`，每个插件先下载再执行，下一个才轮到 | 60 个插件、每脚本 25ms 下载 → 启动 ≈ 1.9s；串行下限就是 Σ(下载+执行) |
| 2 | 插件脚本下载**没有超时**，也没有 AbortController | 一个永不返回的请求让整个插件加载**永久挂起**：实测 9s 观测窗口内 **0 个插件**完成（排在其后的全部陪葬） |
| 3 | 后端**每个请求都全量重建插件列表**：`findAll → discoverAll → discoverPlugins` 遍历插件目录、读取并解压**每一个** `.plugin`（包括没被请求的那些）、重新解析全部 manifest；每行日志一次 `appendFileSync` | 40 个插件下 240 次脚本请求 = 240 次目录重扫、9840 个归档条目解压、1.64MB 无谓解压 |

第 3 条尤其隐蔽：**插件越多，每取一个脚本文件越贵**——这正是「我装的插件越多越卡」的结构性原因。

---

## 2. 新契约（不可变量）

加载器现在承诺：

| 不变式 | 默认值 | 说明 |
|---|---|---|
| 脚本下载并发、有界 | 6 | 61 个插件的下载从「61 次往返」变成「11 批」，且不会一次开 61 个连接 |
| 每个脚本有下载截止时间 | 10 000 ms | 超时的插件被隔离成 `error`，其余照常加载 |
| 求值顺序不变 | — | core 优先、`loadAfter`/`requirements` 生效、`window.plugin` 逐个切换 |
| 定期把主线程还给浏览器 | 每 12 ms | 插件求值期间客户端仍能绘制；`MessageChannel` 宏任务，不触发 `setTimeout` 的 4ms 钳制 |
| 生命周期钩子有预算 | 100 ms | 超标只标记 + 上报，不阻塞其它插件的事件派发 |
| 被门禁跳过的插件不下载 | — | 禁用 / `ncm3-compatible:false` / 版本不满足的插件，计划阶段就不抓脚本 |
| 全部可见 | — | 每个插件的 下载等待 / 脚本执行 / 钩子 耗时都上报到 `betterncm.loader` 与管理器「诊断」页 |

**顺序语义没有变**：这是关键。并发只作用于**下载**，求值仍然严格串行（插件共享 `window.plugin` 和 DOM，
`loadAfter` 只有在顺序求值时才有意义）。所以「更快」不是靠放松契约换来的。

## 3. 框架侧改动（`loader/framework.js` · `0.3.0 → 0.4.0`）

- **有界下载池 `startPrefetch`**：为所有将要加载的脚本建立 deferred promise，按 `concurrency` 并发下载。
  求值阶段 await **自己那个** promise，所以 plugin #1 的脚本一到就开始求值，不必等全套下载完；
  单个慢插件只占自己的槽位。
- **`fetchScript` + `AbortController`**：永远 resolve 成 `{ok:false, timed_out:true, error}`，从不 reject。
  死掉的下载是一条可上报的结果，而不是把共享链掀翻的异常。
- **`yieldIfNeeded`**：距上次让出超过 `yieldBudgetMs` 才让出，最多约每帧一次，避免为「流畅」付出 O(N) 的定时器代价。
  Node 环境下对 `MessagePort` 调 `unref()`，测试工具不会因此挂住事件循环。
- **`pluginGate` 单一裁决**：调度器与 `loadPlugin` 共用同一个门禁函数，因此「不下载会被跳过的插件」
  只可能省掉工作，不可能改变判定。
- **逐插件遥测 + 增量发布**：`window.__BNCM_LOADED__.perf`，并在**每个插件结束时**刷新
  `__BNCM_LOADED__.plugins`。以前只有整批加载完才有快照，于是「卡在第 7 个插件」和「还没开始」看起来一模一样。
- **页面错误归属**：插件作为「当前插件」期间冒出的 `error` / `unhandledrejection` 记录到具体 slug
  （`betterncm.loader.pageErrors()`）。
- **日志批量**：一次请求带多行（`{messages:[...]}`），宿主同时兼容旧的 `{message}`。以前插件的每行日志 = 一次 HTTP 往返。
- **`betterncm.loader`**：`stats()` / `plugins()` / `pageErrors()` / `config` / `configure()` / `reload()`。

## 4. 宿主侧改动（`tools/ncm_host.mjs`）

- **`readZipArchive` 惰性解压**：只解析中央目录；条目字节在**被请求时**才解压并记忆。`readZip` 保留为
  一次性全量读（兼容既有调用方与测试）。
- **插件发现缓存**：`TTL`（默认 1000ms，覆盖加载器的启动突发）+ **目录签名复核**
  （`readdir` + 每项 `stat` 的 mtime/size，一次安装/卸载会改目录 mtime）+ 显式 `invalidateDiscovery()`。
  复核成本与「读并解压所有归档」相差几个数量级。
- **`readDisabled` 按 stat 签名记忆**：它也在每个插件文件请求上被查询。
- **ETag / 304 + `Cache-Control: no-cache`**：插件脚本、`framework.js`、`preload.js`、`manager.js` 都带校验器。
  页面重注入时浏览器用 304 复用脚本；因为 `no-cache` 会重新校验，改了插件立刻生效。
- **新鲜度优先于命中率**：归档插件（生产形态）走字节缓存，而**未打包目录插件直读**——因为改目录里的文件
  不会改变目录自身的 mtime，缓存字节会端出上一版；每次完整扫描还会清空字节缓存，所以「同名替换的归档」
  与「原地改动的目录插件」都拿到新内容（`test/host-scale.test.mjs` 第 3b 节）。
- **日志缓冲**：合并写入 + 定时/退出冲刷，不再是每行一次同步磁盘写。
- **`/api/perf`**：发现缓存命中/重扫、归档解压条目与字节、文件服务与 304、日志冲刷——可机读。
- **`--discovery-ttl-ms N` / `--no-discovery-cache`**：可调，也可回退到旧行为做对照。

## 5. 实测数据

采集脚本：`node tools/bench_scale.mjs`（对照用，一次性）；
回归：`node test/loader-scale.test.mjs`、`node test/host-scale.test.mjs`。
同机重复运行有约 ±5% 波动（Windows 计时器粒度约 15.6ms，测试/基准里的「延迟」都取得比它大）。

### 5.1 框架：每脚本下载 25ms，N 个插件

| 插件数 | 并发 1（≈ 旧串行路径） | 并发 6（新默认） | 纯串行下限 |
|---:|---:|---:|---:|
| 11 | 382 ms | **107 ms** | 275 ms |
| 61 | 1941 ms | **386 ms** | 1525 ms |
| 201 | — | **1108 ms** | 5025 ms |

201 个插件 1.1s：即使插件数翻 3 倍，启动时间也只由「下载批次 + 串行求值」决定，而不是由插件总数直接决定。

### 5.2 隔离：一个脚本永不返回

20 个正常插件 + 1 个永不返回的脚本：

| | 修复前 | 修复后 |
|---|---|---|
| 加载是否完成 | ❌ 9s 观测窗口内 0 个插件完成 | ✅ 368 ms 内完成 |
| 其余插件 | 全部陪葬 | 20/20 `loaded` |
| 问题插件 | 永远停在 `loading`，无错误 | `error: timeout after 300ms ...`，并出现在 `perf.timeouts` |

### 5.3 宿主：40 个插件 + 1 个含 4MB 资源的归档

240 次脚本请求：

| 指标 | 无缓存（旧路径，`--no-discovery-cache`） | 缓存（新默认） |
|---|---:|---:|
| 240 次请求总耗时 | ≈1600 ms（≈6.7 ms/次） | **≈390 ms（≈1.6 ms/次）** |
| 插件目录重扫 | 240 | **0** |
| 归档条目解压 | ≈10 000 | **40** |
| 解压字节 | ≈1.64 MB | **600 B** |

同一个归档只取 `main.js`：

| 读法 | 解压字节 |
|---|---:|
| 旧（`readZip` 全量） | 4 194 490 B |
| 新（`readZipArchive` 按需，取 1 个条目） | **15 B** |

缓存不是靠「过期就不管」换来的：安装新插件后立刻出现在 `/api/plugins`，卸载后立刻 404（`test/host-scale.test.mjs` 第 3 节）。

## 6. 插件作者的契约与已知边界

- **同步死循环无法被抢占**。单线程 JS 里没有安全的抢占手段，框架能做的是：只让它影响自己的加载、
  把它的超时/超预算记录成可归因的数据、并在插件之间让出主线程。**作者仍然不得阻塞主线程**，
  长任务必须切片或异步化。超过 `slowHookMs` 的钩子会被标记并显示在管理器里。
- **同步 eval 的体积成本无法并行**：下载可以并发，`new Function` 求值不能（共享全局与顺序契约）。
  体积大的插件首先给自己加时间——这是它自己的代价，不会转嫁给别人。
- **document 级 reload 语义未变**：第三方插件没有卸载接口，所以 `reloadPlugins()` 仍然合并为一次整页刷新（`docs/17`）。
- **缓存正确性的前提**：插件目录签名 + TTL。若用非文件系统手段（例如在容器里）改插件而 mtime 不变，
  应使用 `--no-discovery-cache`。

## 7. 回归

```powershell
node test\loader-scale.test.mjs    # 33 项：并发/超时隔离/顺序/遥测/预算/跳过不下载
node test\host-scale.test.mjs      # 34 项：惰性解压/发现缓存/新鲜度/ETag/批量日志/计数器
node test\framework-api.test.mjs   # 59 项：框架 API 契约（含 0.4.0 契约）
node test\plugin-reload.mjs        # 重复/并发 reload → 仅一次整页刷新、不重复执行插件
node test\dev-source.test.mjs      # 59 项：dev mode（宿主改动回归）
```

后两个套件加上 `framework-api` 都不需要客户端，是改动加载器/后端后的必跑项。
`test/lib/bncm-harness.mjs` 是可复用的假客户端（真实计时器、可注入延迟/挂起/失败），新测试复用它而不是各自造轮子。
